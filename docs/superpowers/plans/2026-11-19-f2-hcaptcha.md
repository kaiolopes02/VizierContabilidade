# F2 hCaptcha Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fechar o achado F2 da auditoria (run-4) — o formulário do site passa a exigir um token hCaptcha válido, validado **server-side pelo Web3Forms**, bloqueando POST direto sem token.

**Architecture:** O modal (`public/js/main.js`) renderiza um widget hCaptcha (script do hCaptcha carregado sob demanda, `render=explicit` porque o modal é criado dinamicamente). O hCaptcha injeta `<textarea name="h-captcha-response">` dentro do `<form>`; o `FormData` já leva o token; o Web3Forms valida o token no servidor e rejeita submissões sem token válido. O cliente apenas bloqueia o envio quando o token está ausente (gate explícito) e reseta o widget após falha de envio. **Sem backend**: não há `functions/`, não há Worker, não há chave secreta no código.

**Tech Stack:** HTML/CSS/JS estático (sem framework, sem `package.json`, sem dependências novas), Cloudflare Pages (arquivos estáticos + `_headers` CSP), Web3Forms (free) + hCaptcha.

**Spec:** `docs/superpowers/specs/2026-11-19-f2-hcaptcha-design.md` (o spec é a autoridade; este plano é seu argumento)

## Global Constraints

- **Sem backend**: não criar `functions/`, não criar Worker, não reintroduzir proxy; o envio continua direto do navegador para `https://api.web3forms.com/submit`.
- **Preservar visual e classes não relacionadas**: não mexer em `public/css/main.css`, não reordenar campos do formulário, não mudar o layout do modal. Nenhuma classe existente pode ser removida.
- **Sem `innerHTML` com dado de usuário**: o markup do modal é estático; nenhum valor de campo entra em `innerHTML`.
- **Valores exatos**: `HCAPTCHA_SITEKEY = '50b2fe65-b00b-4b9e-ad62-3ba471098be2'` (sitekey compartilhado do Web3Forms para planos grátis) e `HCAPTCHA_SCRIPT = 'https://js.hcaptcha.com/1/api.js?render=explicit&onload=vizierHCaptchaReady'`.
- **`access_key` do Web3Forms não muda**: `6a9190b9-2c91-4546-9abe-e394fc0554bb` (chave pública por design do provedor).
- **Gate antes do FormData**: a leitura de `h-captcha-response` e o `return` devem acontecer **antes** de `const formData = new FormData(form);`.
- **CSP**: permitir `https://hcaptcha.com https://*.hcaptcha.com` em `script-src`, `frame-src` e `connect-src`. `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action` e `upgrade-insecure-requests` **inalterados**.
- **i18n**: a chave `modal.captchaErro` existe nos 3 dicionários de `public/js/i18n.js` (`pt-BR`, `en-US`, `es`).
- **Escopo fechado**: não tocar em `wrangler.jsonc`, no F1 (chave StaticForms no cache do edge), no layout/CSS, nem criar dependências.
- **Sem push, sem merge, sem deploy**: todo o trabalho fica em commits locais na branch `fix/f2-hcaptcha`.

## Review Focus

1. **Modal reaberto**: o widget renderiza uma única vez e o token anterior (expirado/consumido) não bloqueia o novo envio → reset no `close()`.
2. **Falha de envio (timeout/offline)**: o token é de uso único, então o widget precisa ser resetado no `catch()` — sem isso o visitante fica preso unable to reenviar.
3. **Token válido + outro campo inválido**: o erro do campo aparece e **nenhum** request sai (o gate não pode rodar antes das validações existentes).
4. **hCaptcha ainda carregando**: se o visitante clicar em Enviar antes do script carregar, o gate deve barrar com mensagem clara (sem `fetch`), nunca com `undefined`/exceção.
5. **Acessibilidade**: a mensagem de erro do captcha precisa ser anunciada (o `showSubmitError` já cria `div[role=alert]`) e o widget não pode quebrar o `trapFocus` do modal.
6. **CSP em runtime**: o widget só funciona se `script-src`, `frame-src` e `connect-src` liberarem as origens do hCaptcha — `frame-src` hoje é `'none'`.

Carregamento **sob demanda** (o script só entra quando o modal é aberto pela primeira vez, e apenas uma vez):

```js
let hcaptchaWidgetId = null;
let hcaptchaLoading = false;
let hcaptchaFailed = false;

const ensureHCaptcha = (container) => {
  if (!container) return;
  const render = () => {
    if (hcaptchaWidgetId !== null || typeof window.hcaptcha === 'undefined') return;
    const widgetId = window.hcaptcha.render(container, { sitekey: HCAPTCHA_SITEKEY });
    if (widgetId) hcaptchaWidgetId = widgetId;
  };
  if (typeof window.hcaptcha !== 'undefined') { render(); return; }
  if (hcaptchaLoading) return;
  hcaptchaLoading = true;
  const s = document.createElement('script');
  s.src = HCAPTCHA_SCRIPT;
  s.async = true;
  s.defer = true;
  s.addEventListener('load', () => {
    setTimeout(() => {
      if (hcaptchaWidgetId === null) render();
    }, 50);
  }, { once: true });
  s.addEventListener('error', () => {
    hcaptchaFailed = true;
    s.remove();
  }, { once: true });
  window.vizierHCaptchaReady = render;
  document.head.appendChild(s);
};
```

Chamar `ensureHCaptcha(overlay.querySelector('#hcaptcha-widget'))` dentro de `open()` (depois de `overlay.classList.add('active')`, quando o container já está visível).

Gate no submit handler — o `const formData = new FormData(form);` atual (que hoje fica logo após o bloco `if (!valid) { ... return; }`) é **movido para depois** do gate, e o gate entra depois dos helpers `showSubmitError`/`clearSubmitError` (para poder reusar `showSubmitError`, que cria `div[role=alert]`):

- [ ] **Step 3c: Renderizar o widget pelo callback `onload` do hCaptcha**

> Amendment do controller (2026-11-19): originado na **verificação em navegador real** do controller (probe Edge headless + CDP sobre `e7d3048`). O console do navegador registrou `[hCaptcha] should not render before js api is fully loaded. render=explicit should be used in combination with onload.`
>
> Causa (confirmada no bundle oficial `https://js.hcaptcha.com/1/api.js?render=explicit`): `window.hcaptcha` é definido de forma **síncrona**, mas a inicialização da API é adiada por `setTimeout(..., 1)`. O listener `load` do `<script>` dispara **antes** dessa inicialização, então `hcaptcha.render()` é chamado com a API ainda não pronta (a flag interna `a` do bundle ainda é `false`). O próprio hCaptcha exige `render=explicit` combinado com `onload` — sem isso, o `render` pode falhar silenciosamente e o widget não aparecer (o mesmo modo de falha do Critical já corrigido: todo envio legítimo barrado).
>
> **Ruling do controller:** o valor literal de `HCAPTCHA_SCRIPT` muda de `https://js.hcaptcha.com/1/api.js?render=explicit` para `https://js.hcaptcha.com/1/api.js?render=explicit&onload=vizierHCaptchaReady`. Host, path, `render=explicit` e a `sitekey` permanecem idênticos; nenhuma outra URL, dependência ou backend entra no patch. Custo se a decisão estiver errada: um parâmetro de query e um callback global; o caminho feliz permanece o mesmo.

Em `public/js/main.js`:
- constante `HCAPTCHA_SCRIPT` com `&onload=vizierHCaptchaReady`;
- antes de anexar o `<script>`, definir `window.vizierHCaptchaReady` (o bundle resolve o callback por `window[nome]`) apontando para a função de render já existente;
- o callback chama a mesma função `render()` que hoje roda no listener `load` — **não** haver render duplicado: a guarda `hcaptchaWidgetId !== null` continua valendo;
- o listener `load` passa a ser apenas um **fallback tardio** (`setTimeout` de ~50 ms) que só renderiza se o callback ainda não tiver renderizado (protege contra uma versão futura do hCaptcha que ignore o parâmetro `onload`);
- `hcaptchaWidgetId` só é atribuído quando `render()` devolve um ID verdadeiro (assim uma renderização sem retorno permite o retry do fallback);
- o listener `error` e a flag `hcaptchaFailed` permanecem como estão (Step 3b).

Em `tests/forms.mjs`, checks novos:
- a URL do script contém `render=explicit` **e** `onload=vizierHCaptchaReady`;
- `window.vizierHCaptchaReady` é atribuído **antes** de `document.head.appendChild(s)`;
- o callback chama a função de render e não há segunda chamada de `render` fora do callback/fallback;
- o fallback renderiza somente quando `hcaptchaWidgetId === null`.

Mutação anti-vazia exigida: remover o `&onload=…` da URL e/ou mover a atribuição do callback para depois do `appendChild` ⇒ `forms.mjs` deve **falhar**; restaurado ⇒ passa.
